# Magic Mirror: personal persona and avatar memory — 2026-10-04

Companion to the [Apple Silicon voice-stack survey](apple-silicon-voice-stack-survey-2026-10-04.md). Scope: evidence-based research and a proposed design, not an implementation or an import of personal information.

## Conclusion

Moving to local STT → cloud text model → local TTS separates speech from reasoning. It does not automatically transfer a personal ChatGPT assistant or create lasting avatar memory. Persona instructions and application-managed memory can support either this pipeline or the current Realtime backend. The useful architectural change is to make those two layers independent of the speech backend.

“Verified” means supported by inspected repository code or a primary source accessed on 2026-10-04. “Proposed” means a recommendation. “Unverified” means behavior or access still needs an experiment. No private ChatGPT history, stored memories, credentials or conversation recordings were read for this survey.

## What can move from a personal ChatGPT assistant?

**Verified:** ChatGPT personalization includes distinct controls for personality, custom instructions and memories. Communication style is different from remembered personal context. These are product features, not properties automatically attached to every API request made by the same account. [OpenAI personalization documentation](https://learn.chatgpt.com/docs/personalize).

**Verified:** Sign in with ChatGPT does not give an application access to the user's ChatGPT conversations or memories. It can authorize eligible model usage; it is not a transfer of the assistant's personal history. [OpenAI sign-in documentation](https://learn.chatgpt.com/docs/sign-in-with-chatgpt).

**Proposed transfer approach:**

| Existing material | Transfer into Magic Mirror | Limit |
| --- | --- | --- |
| User-authored character instructions and response preferences | An editable avatar persona definition | Reusing instructions does not guarantee identical behavior from a different model. |
| Selected personal facts and relationship context | A reviewed private seed-memory import | OAuth does not fetch them. The user must select/provide the content through a separately designed import. |
| Custom GPT knowledge files | An avatar knowledge library with retrieval | File permission, indexing and retrieval must be implemented; media playback folders are not a knowledge index. |
| Custom GPT actions or connected services | Explicit Magic Mirror tool integrations | They do not become available merely by copying the prompt. |
| ChatGPT voice and conversational manner | Separately selected TTS voice and speaking instructions | This is a recreation, not a verified export of the existing voice experience. |

For a custom GPT, OpenAI's migration guide treats instructions, knowledge files, actions and model selection as separate migration concerns. That guide describes migration to ChatGPT plugins, not an automatic export into Magic Mirror; it supports the component distinction, not a claim of a one-click importer. [OpenAI custom GPT migration guide](https://learn.chatgpt.com/docs/migrate-custom-gpts).

**Unverified:** A complete, fidelity-preserving export of the user's particular assistant, all memories, hidden product context and behavior. No such capability was established by this research. A summary generated by an assistant should be treated as a draft to review, not proof that every memory transferred.

## Realtime versus a local speech harness

| Concern | Current Realtime approach | Proposed local STT / cloud text / local TTS |
| --- | --- | --- |
| Persona | Instructions supplied to the Realtime agent | Instructions supplied to the text agent; speaking controls also supplied to TTS |
| Current conversation | Realtime session holds conversation items | Application manages context and supplies it to the cloud model |
| Memory across restarts | Requires a separate memory feature | Also requires a separate memory feature |
| Importing ChatGPT personalization | No automatic import established | OAuth does not provide one |
| Voice performance | Audio understanding, reasoning and speech in one session | Recognition, reasoning and synthesis are independently replaceable |
| Memory extraction input | Application can use completed conversation text | Application can use the STT result and completed assistant response |
| Control and failure points | Session and audio event lifecycle | Additional recognition, text-generation and synthesis boundaries |

**Verified:** Realtime sessions contain conversation items and configurable instructions. That session context is not evidence of persistent personal memory in our application. [Realtime conversation documentation](https://developers.openai.com/api/docs/guides/realtime-conversations).

**Verified:** OpenAI distinguishes speech-to-speech sessions from a chained pipeline in which the application controls STT, the agent workflow and TTS independently. [Voice architecture documentation](https://developers.openai.com/api/docs/guides/voice-agents).

**Inference:** A plain transcript does not encode every acoustic cue in the original speech. A text-only reasoning path will receive only the words and any explicitly supplied annotations. Its conversational feel may therefore differ even with identical persona text. STT mistakes can also become mistaken candidate memories unless important details are confirmed. Neither the size of this difference nor the local models' quality on this Mac has been measured.

**Verified OAuth-specific limitation:** The currently documented HTTP route requires `store:false`, `stream:true` and caller-supplied context; it does not support HTTP continuation through `previous_response_id`. WebSocket continuation is limited to the same authenticated connection. Do not assume that general Responses conversation-storage features are available on this route. [Sign-in preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).

**Unverified eligibility:** OpenAI's quickstart describes availability for open-source partners and selected private clients. This personal project's eligibility and successful authenticated inference still need confirmation; being noncommercial alone does not establish eligibility. [Sign-in quickstart](https://developers.openai.com/siwc/quickstart).

## What Magic Mirror actually implements today

**Verified persona wiring:** [avatar-prompt.ts](../src/shared/avatar-prompt.ts) defines and renders public avatar settings including name, personality and speaking style. [realtime-session-adapter.ts](../src/renderer/realtime/realtime-session-adapter.ts) supplies that prompt as the Realtime agent's instructions. This is a real working integration point for an imported character definition.

**Verified memory gap:** [module-registry.ts](../src/main/module-registry.ts) defaults memory to `not_implemented`. More decisively, [field-help-text.ts](../src/renderer/console/field-help-text.ts) explicitly describes the extraction-model setting as a simulated role that does not enable memory storage. Inspection of the transcript callback in [mirror/App.tsx](../src/renderer/mirror/App.tsx), Main wiring and memory-related references found no implemented durable extraction/write/retrieval pipeline. A model selector and planned extraction contract do not constitute working memory.

**Verified privacy boundary:** [DECISIONS.md](../DECISIONS.md) currently requires transcripts, audio, extracted memory values and injected private context to remain RAM-only. Existing SQLite infrastructure does not override that rule. Persistent avatar memory therefore requires a deliberate revision of the data-lifecycle design before implementation. This research changes no rule and writes no personal memory.

## Recommended design for the user's two goals

The following is **proposed**, not existing functionality.

1. **Keep one editable persona per avatar.** Import the user's own character instructions and preferences into a review screen. Separate public character lore from private facts about the owner. Use the same persona source for both conversation backends. OpenAI documents identity, instructions, examples and context as distinct prompt components. [Prompt engineering guidance](https://developers.openai.com/api/docs/guides/prompt-engineering).
2. **Give the avatar its own application-managed memory.** Store approved facts and concise relationship/event records locally, independent of a cloud session. Scope private records by avatar and confirmed person. Keep global sharing explicit. The cloud account paying for inference is not proof of the identity of the person at the mirror.
3. **Retrieve only relevant, permitted memories into each turn.** Keep guest/profile identifiers in Main. Load private context only after the existing verbal-confirmation requirement. Retrieved text sent to the cloud is no longer local-only, even when its database resides on the Mac.
4. **Make remembering deliberate and correctable.** Support explicit remember/forget requests and a Console list with edit/delete controls. Treat automatic extraction as a candidate, with contradiction handling and confirmation for consequential or uncertain facts. Capture the memory owner at turn start; retain existing exclusions for control turns.
5. **Keep raw conversations ephemeral.** A revised persistence rule could allow selected structured memories while retaining RAM-only audio/transcripts. Define deletion, backups and retention before saving real data. No personal content belongs in repository files, diagnostics or research artifacts.

A simple Console can expose two sections per avatar: **Persona** for instructions and speaking style, and **Memories** for import/review/edit/delete. Voice selection remains a separate control. Ordinary memory management should not require choosing databases, embedding models or extraction prompts.

Start with the existing Main-owned SQLite capability and simple bounded retrieval for a small personal collection. Add semantic indexing only if measured recall quality requires it. This is a scope recommendation, not a benchmark result.

## Acceptance evidence needed before claiming success

Use synthetic fixtures for automated checks; use real private content only through an explicitly designed private runtime flow.

- A selected imported preference changes an answer appropriately on both backends.
- A saved memory survives a restart, can be corrected, and stops being retrieved after deletion.
- Another avatar or unconfirmed visitor cannot retrieve private memories.
- A profile switch cannot misattribute a memory from an earlier turn.
- Misrecognized speech does not silently overwrite a confirmed fact.
- Interrupted or unplayed generated speech is not recorded as something the user heard.
- Prompt and voice comparison establishes acceptable character consistency, Mandarin recognition, latency and interruption behavior on this Mac.

Recommendation: design the persona/memory layer once and make it work with the existing Realtime backend first. Prototype local STT/TTS as a separately measurable speech change. This gives the user continuity without making lasting memory depend on an unproven speech migration.

Validation for this research is source inspection and Markdown static checks. No application behavior, credentials, runtime models, database schema or deployment was changed.

## Follow-up: lasting memory on the current Realtime architecture

Research date: 2026-10-04. Both companion surveys were reread. Recommendation: implement application-owned memory while retaining Realtime. A speech-backend migration is unnecessary for this goal. The following is a design survey, not implemented behavior.

### Verified model and API boundaries

**Verified repository configuration:** [default.json](../resources/config/default.json) selects `gpt-realtime-2.1-mini` for dialogue, `gpt-live-transcribe` for transcription, and `gpt-5.6-luna` for the future extractor. [model-settings.ts](../src/main/model-settings.ts) freezes the published model configuration into session/job snapshots. **Unverified:** the running application's published configuration may override the packaged default; no live configuration database or private session was inspected. Implementation must use the actual session snapshot, not hard-code these defaults.

| Boundary | Evidence | Design implication |
| --- | --- | --- |
| Context window | **Verified:** `gpt-realtime-2.1-mini` lists 128,000 context tokens and 32,000 maximum output tokens. [Model page](https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini) | Context includes more than the persona: instructions, tools, conversation, audio, images and retrieved records compete for capacity. The output maximum is a capability, not a suggested reply length or a guaranteed accepted numeric session setting. |
| Separate instruction ceiling | **Unverified for this exact model:** the older GA article states 16,384 tokens for instructions plus tools for the original `gpt-realtime`. [Historical GA explanation](https://developers.openai.com/blog/realtime-api) | Do not present that older limit, its 32,768-token context, or its 28,672-token input allowance as the limits of 2.1 Mini. Keep our own substantially smaller budget and verify the exact accepted session configuration during implementation. |
| Session duration | **Verified:** the current Realtime conversation guide specifies a maximum of 60 minutes. [Session lifecycle](https://developers.openai.com/api/docs/guides/realtime-conversations) | Rebuild relevant context on a replacement session. A large token window does not remove session expiry. |
| Overflow | **Verified:** older items can be excluded by truncation; disabling truncation causes an error when input is too long. The GA explanation says dropped items are not automatically summarized. [Truncation](https://developers.openai.com/api/docs/guides/voice-latency-cost), [GA behavior](https://developers.openai.com/blog/realtime-api) | Treat the database as the source of truth. Never rely on an early conversation item remaining available indefinitely. |
| Reliable memory writes | **Verified:** 2.1 Mini supports function calling but does not advertise Structured Outputs. [Model capabilities](https://developers.openai.com/api/docs/models/gpt-realtime-2.1-mini) | Validate every memory tool call in Main. A spoken promise to remember is not a database commit. Use a separate schema-constrained extractor for automatic candidates, subject to its configured model's verified support. |
| Transcript timing | **Verified:** completed transcription events from different turns can arrive out of order; match them by input item ID. [Transcription events](https://developers.openai.com/api/docs/guides/realtime-transcription) | Bind ownership when the turn begins, not when text eventually arrives. Do not assume a transcript callback runs before Realtime starts answering. |

**Verified guidance:** OpenAI recommends short labeled prompt sections and distinguishing current authoritative context from historical background. A bigger window does not remove the need to resolve conflicting records. [Realtime prompting](https://developers.openai.com/api/docs/guides/voice-prompting).

**Verified cost behavior:** conversation items become input to later responses. Changing early instructions/tools reduces prefix-cache reuse. Retention-ratio truncation can drop a larger block at once to reduce repeated cache disruption. [Realtime cost guidance](https://developers.openai.com/api/docs/guides/voice-latency-cost).

### Current implementation findings

- **Verified:** [avatar-prompt.ts](../src/shared/avatar-prompt.ts) limits personality to 12,000 characters and speaking style to 2,000 characters. Those are character checks, not a combined token budget. It embeds the enabled media resource list as JSON alongside persona and tool instructions. [media-skill.ts](../src/shared/media-skill.ts) permits up to 512 resources, each with aliases; resource growth can consume prompt space independently of memory.
- **Verified:** [realtime-session-adapter.ts](../src/renderer/realtime/realtime-session-adapter.ts) creates the agent with this prompt and registered tools. It disables audio history and tracing. Its session options do not set a context budget or truncation policy, and its `response.done` branch does not collect usage for context management.
- **Verified:** the adapter enables automatic responses after turn detection. [mirror/App.tsx](../src/renderer/mirror/App.tsx) routes completed input transcripts to scene handling; it does not implement memory extraction or retrieval. Adding a database lookup to this callback would not prove that the current answer received the result in time.
- **Verified:** [realtime-recovery.ts](../src/shared/realtime-recovery.ts) sets rollover to 3,600,000 ms; [boot.ts](../src/main/boot.ts) arms that timer. This leaves no deliberate margin before the documented 60-minute expiry. **Proposed:** initiate rollover at an idle boundary around 55 minutes, with a bounded deadline before expiry; test actual audio/mic handoff.
- **Verified:** memory and identity are marked `not_implemented` in [module-registry.ts](../src/main/module-registry.ts). The reviewed path has no durable memory writer, retriever, or completed private-owner confirmation workflow. Identity confirmation must be part of memory delivery, not assumed to exist because its rules are documented.
- **Verified local SDK surface:** installed Agents SDK 0.16.1 exposes session usage, agent updates and initial-session configuration computation. Installed OpenAI types expose retention-ratio truncation. These are integration surfaces, not evidence that our adapter already uses them or that a particular configuration has passed a live contract test.

### Proposed small architecture

Keep three distinct kinds of state:

| State | Purpose | Lifetime |
| --- | --- | --- |
| Avatar persona and public lore | Who Raven is and how Raven speaks | Operator-controlled configuration |
| Private lasting memories | Confirmed preferences, relationships, selected events and ongoing commitments | Local Main-owned database, scoped to avatar plus confirmed person |
| Working conversation summary | Current topic, unresolved question and recent progress | RAM; transferred only across an authorized same-owner rollover, cleared on sleep/owner change/restart |

The lasting collection may grow without putting every record into the prompt. On owner confirmation, retrieve a compact set of core facts and recent relevant commitments. Add a bounded `recall_memory` tool for questions requiring older details. Tool requests do not carry guest IDs: Main selects the authorized owner from its session state. Recheck owner/session generation after asynchronous retrieval before releasing any result.

Keep stable persona and tool instructions stable. Supply selected memory as explicitly labeled reference data with dates, status and provenance, separate from instructions. Treat remembered text and imported files as data, never authority to execute commands. Do not repeatedly append the same facts or rewrite the whole persona every turn. Enforce the budget across both initial memory and later recall results.

**Realtime timing choice:** preload core memories after confirmation so ordinary speech stays immediate; require a recall result before answering a question about historical details not present in context. Tool-based recall adds latency only when needed. Model compliance with the recall instruction needs evaluation. If deterministic retrieval before every answer becomes necessary, automatic response creation must be replaced with application-controlled response scheduling; that is a larger latency/turn-taking change, not something to hide inside a transcript callback. Preserve the current speech path for the first implementation.

Start with SQLite and bounded filtering/ranking using importance, recency and query terms. Evaluate Traditional Chinese, English names and paraphrases; basic lexical matching must not be advertised as semantic recall. Add semantic retrieval only if the recall evaluation establishes a need. No separate vector service is required for the first usable version.

### Proposed initial context budget

These numbers are engineering starting points, **not OpenAI limits or measured optimal values**:

| Component | Initial target |
| --- | --- |
| Persona, application rules, tool definitions and compact resource context combined | Up to 4,000 tokens |
| All currently supplied private memory excerpts combined | Up to 1,500 tokens |
| Current working summary | Up to 500 tokens |
| Recent conversational items and tool results | Bounded separately; trial a 16,000-token post-instruction window |

The roughly 6,000-token prepared context target leaves substantial room within the documented 128k window. Overlapping categories must be counted once according to their actual wire placement. Start with brief memories and a few relevant records; never split a fact mid-sentence to fit. Reduce low-priority retrieved records first. Preserve control/security instructions. If the operator's persona alone exceeds its allocation, provide a clear validation result instead of silently deleting character instructions.

A trial retention ratio of 0.8 with a bounded `post_instructions` window is reasonable, but verify the installed SDK serialization and provider acceptance before enabling it. That field excludes instructions/tool definitions; it is not a cap on the entire request. The model's 32,000 output capability does not establish which explicit `max_output_tokens` values this session API accepts. Do not infer those values from the model card alone.

Measure the assembled configuration and actual per-response usage, including audio/image input. Character counts, English word ratios and cumulative session usage are not current-context measurements. Keep only token counts, cache counts, durations, status and reason codes in diagnostics. Full prompts, retrieved memory and tool-result content must remain out of the prompt inspector and logs.

Avoid allowing the complete media catalog to dominate the stable prompt. Preserve existing media behavior with bounded discovery/search results when the catalog exceeds the allocation. This is relevant budget work, not permission to redesign unrelated media UI.

### Remembering, corrections and deletion

Implement explicit remember, recall and forget first, plus a simple per-avatar **Memories** Console page with search, edit and delete. Show who the memories belong to in the authorized operator view. Realtime may report a successful save only after Main returns a successful commit. Read or write failures produce an understandable result without stopping unrelated conversation.

Next, add optional automatic extraction of useful facts and concise event records from completed ordinary turns. Use the configured extractor's frozen job snapshot and schema validation. Never infer personal facts from Raven's fictional claims, hypothetical stories or unheard response tails. Keep candidates distinct from confirmed facts; uncertain or consequential details require confirmation. New corrections supersede older facts instead of leaving contradictory active records.

Snapshot the owner at turn start; match late events by session/item IDs; deduplicate writes. Identity, naming, switch, group, sleep and spell control turns remain excluded. Memory-management commands should be handled deliberately and excluded from general extraction so that a forget request cannot recreate its own content. Earlier ordinary turns may finish their independently authorized extraction, subject to cancellation and owner checks.

Deletion must invalidate loaded excerpts, pending writes and working summaries that could restore the deleted fact. A deleted fact already present in a cloud session needs that context removed or a clean rebuilt session before claiming it is forgotten in conversation. Owner changes require a clean session and renewed confirmation; another avatar cannot automatically inherit private records.

The existing RAM-only ruling must be revised as part of implementing the requested lasting memory: permit selected structured memories in the private local store while leaving raw transcripts/audio and incidental summaries ephemeral. Define local-file access, backup/retention and deletion behavior explicitly. This survey changes no ruling. API credentials remain under existing invariant 12; persistent memory does not require OAuth or a new credential source. Retrieval sends selected records to the cloud, so local storage does not mean local-only processing.

### Focused delivery and proof

Proposed implementation order: establish the persistence exception and confirmed-owner lifecycle; deliver local storage plus Console CRUD and explicit voice tools; integrate bounded recall/context rollover; then add automatic extraction if desired. Reuse the versioned shared tool catalog and explicit bindings. Keep the memory service independent of Realtime so a future local STT/TTS backend can reuse it.

Required evidence before calling it lasting memory:

1. A synthetic saved fact survives a process restart and is recalled after owner confirmation; a fresh unconfirmed visitor cannot retrieve it.
2. Cross-avatar reads, owner-switch races and delayed transcript/extractor completions cannot leak or misattribute records.
3. Corrections replace stale facts; deletion removes recall and cannot be undone by an in-flight job or old summary.
4. Oversized persona/media/memory fixtures remain within the assembled budget or fail visibly; long conversations retain selected important facts through truncation and rollover.
5. Missing transcripts, extraction failure, recall timeout and database errors preserve conversation and never produce a false save acknowledgement.
6. Real Mac voice QA covers Mandarin recall/paraphrases, interruption, dormant/media transitions and rollover; measure recall accuracy, added response latency and usage counts without recording private content.

**Unverified until implementation/QA:** exact running model, actual assembled prompt tokens, provider acceptance of chosen truncation/output settings, memory recall quality, latency and cross-session continuity. No runtime changes, private-data import, model replacement or app restart were performed for this follow-up.

## Comparison: local speech harness with GPT-6.1 Sol

The user's `gpt-sol-6.1` is interpreted as the documented model ID `gpt-6.1-sol`; no official model with the former spelling was established. Here, “local” means STT, TTS, wake detection and memory storage on the Mac, with Sol inference in OpenAI's cloud. No downloadable/self-hosted Sol deployment was established by this survey.

**Verified:** Sol supports text/image input, text output, Responses tool calling and Structured Outputs; audio is unsupported. Its model page lists 1,050,000 context tokens and 128,000 maximum output tokens. Reasoning starts at `low`; `none` and `minimal` are unsupported. [GPT-6.1 Sol documentation](https://developers.openai.com/api/docs/models/gpt-6.1-sol).

| Concern | Existing Realtime architecture with application memory | Local STT → cloud Sol → local TTS |
| --- | --- | --- |
| Lasting memory | Main-owned persistence/retrieval required | The same persistence/retrieval required; changing models does not create memory |
| Context capacity | Packaged 2.1 Mini: 128,000 tokens | Sol: 1,050,000 tokens; more room for complex context, still use bounded retrieval |
| Retrieval before answering | Preloaded context plus recall tools; automatic voice responses complicate mandatory per-turn retrieval | Application can retrieve and resolve context before sending each text request |
| Candidate memory extraction | Separate structured extractor, with Main validation | Sol supports structured extraction; still validate semantics, ownership and writes in Main |
| Persona and relationship reasoning | Must measure fidelity with the actual Raven prompt and memory set | Plausible candidate for better complex reasoning; no task-specific superiority established |
| Speech | Model directly processes voice; existing interruption/audio pipeline | STT errors and local TTS quality affect the result; application owns the extra scheduling/cancellation boundaries |
| Latency | Existing deployed baseline, not remeasured here | Extra stages plus Sol reasoning; cannot claim faster or slower end-to-end without a Mac comparison |
| Raw audio exposure | Realtime receives conversation audio | Local STT/TTS can retain raw audio locally; selected text/memories still reach cloud Sol |
| Migration work | Memory/identity/context integration | The same memory work plus replacement speech orchestration, model loading and voice QA |

The architecture distinction is documented: Realtime combines audio, reasoning and tools; a chained workflow gives the application control of intermediate text and independently replaceable stages. [OpenAI voice architecture guide](https://developers.openai.com/api/docs/guides/voice-agents). The table's control, quality and engineering assessments are **inferences/proposals**, not measured benchmark results.

**Would Sol be better?** It provides more context capacity and a more controllable text workflow. Better Raven personality, correct recollection, relationship continuity and conversational feel remain **unverified**. No primary-source head-to-head evaluation for this application's task was found. A large context window cannot repair wrong-owner retrieval, contradictory records, inaccurate transcription or a missing database.

**Proposed recommendation:** build the shared lasting-memory service on Realtime first. Compare Sol at `low` with identical persona, authorized retrieved records and tools. If it improves reasoning but local speech is unsatisfactory, evaluate Sol as an optional memory-consolidation or complex-query tool behind the existing voice interface. This hybrid is a proposed separate integration, not an existing feature or an automatic runtime fallback. Keep one owner for the final answer and never allow both models to execute the same action.

For a fair comparison, separate model quality from speech quality: first test identical text/context fixtures, then test both complete voice pipelines on this Mac. Score correct recall, appropriate abstention when no record exists, correction handling, persona consistency, false memory claims, tool success, first-audible-response latency, interruption and cost. Use synthetic fixtures and metadata-only results. Do not select a winner from vendor positioning or context size alone.

**Authentication caveat:** general Sol API capabilities do not automatically describe the Sign in with ChatGPT route. That route requires streaming, caller-supplied HTTP history and `store:false`; HTTP `previous_response_id` is unavailable and tool representation differs. Exact structured-output request support, model access and private-client eligibility still need verification. [OAuth preview contract](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations). The API-key route can test the architecture separately from OAuth eligibility; no credential or runtime configuration changes are made here.
